# NOX Firestore 読み取り専用監査 実行手順書

## 1. 目的と適用範囲

この文書は `scripts/audit-data.js` を将来、安全に実行するための手順と判定基準を定義する。現フェーズでは手順書の作成だけを行い、スクリプト実行、認証設定、IAM変更、Firebase操作、データ移行は行わない。

監査対象は次の8コレクションである。

- `users`
- `stores`
- `jobs`
- `applications`
- `jobEntries`
- `jobApplications`
- `jobViewStats`
- `storeViewStats`

このスクリプトは Firebase Admin SDK を使用する。サーバークライアントは Firestore Security Rules を迂回し、IAMで認可されるため、読み取り専用IAMを必須の安全境界とする。

## 2. 実行責任と承認

- 実行責任者とレビュー担当者を分ける。
- 実行ごとに、対象Google CloudプロジェクトID、予定日時、実行者、出力先、見積もり読み取り数についてリポジトリ所有者の明示承認を得る。
- 承認は恒久的なものとせず、1回の監査実行に限定する。
- 承認されたプロジェクトID以外では実行しない。
- 本番への書き込み、Rules変更、Storage/Auth操作、データ移行を同じ作業に含めない。

## 3. 必要IAM権限

### 3.1 監査用サービスアカウント

専用の単一用途サービスアカウントを作成し、対象プロジェクトに次だけを付与する。

| 対象 | ロール | 用途 |
|---|---|---|
| 対象Google Cloudプロジェクト | Cloud Datastore Viewer (`roles/datastore.viewer`) | Firestoreエンティティの取得・一覧など、監査に必要な読み取り |
| 監査用サービスアカウント自身 | Service Account Token Creator (`roles/iam.serviceAccountTokenCreator`) | 指定実行者が短期認証でサービスアカウントを偽装する場合のみ |

`roles/iam.serviceAccountTokenCreator` は実行者に対して、プロジェクト全体ではなく監査用サービスアカウントのリソース上で付与する。監査用サービスアカウントには、次を付与しない。

- `roles/owner`
- `roles/editor`
- `roles/firebase.admin`
- `roles/datastore.owner`
- `roles/datastore.user`
- 書き込み・削除・インポート・エクスポートを含むカスタムロール

`roles/datastore.viewer` はコレクション単位ではなく、プロジェクト内Firestoreデータ全体の読み取りを許可する。このため、認証期間、実行者、出力先を限定し、実行後に偽装権限を除去する。

### 3.2 IAMの事前確認

- 対象プロジェクトがNOX本番プロジェクトと完全一致している。
- 監査用サービスアカウントに書き込み権限がない。
- 実行者の個人アカウントに、監査のためだけの広域ロールを追加していない。
- サービスアカウント偽装を使う場合、Service Account Credentials APIが利用可能である。
- IAM変更自体について、別途管理者の承認と記録がある。

## 4. サービスアカウント運用方針

優先順位は次のとおりとする。

1. 短期資格情報を使うサービスアカウント偽装
2. 管理されたGoogle Cloud実行環境にアタッチした専用サービスアカウント
3. 上記が不可能で、例外承認を得た場合のみサービスアカウントJSON鍵

ローカル実行では、Node.jsのApplication Default Credentialsに対応する次の偽装方式を第一候補とする。

```powershell
# 将来の承認済み作業でのみ実行する例
gcloud auth application-default login --impersonate-service-account AUDIT_SERVICE_ACCOUNT
$env:FIREBASE_PROJECT_ID = "APPROVED_PROJECT_ID"
```

長期JSON鍵は原則発行しない。例外的に使用する場合は、リポジトリ外のアクセス制限された一時ディレクトリに置き、ファイル名や内容をログ、チャット、Issue、CI成果物へ残さない。既定サービスアカウントや既存の高権限サービスアカウントを監査に流用しない。

- [ ] Node.jsと `firebase-admin` のバージョンを実行記録に残す
- [ ] 実行端末が共有端末ではなく、OS更新とマルウェア対策が有効である

### 5.2 対象と認証

- [ ] `FIREBASE_PROJECT_ID` を明示し、承認されたプロジェクトIDと照合した

- [ ] 監査主体のIAMが `roles/datastore.viewer` の範囲内である
- [ ] 書き込み可能な別資格情報が環境変数や既定ADCに残っていない

### 5.3 費用と運用

- [ ] 出力先はリポジトリ外で、アクセス権が実行者とレビュー担当者だけに限定されている
- [ ] 保存期間と削除予定日を決めた
- [ ] 失敗時に再実行せず、まず原因と発生読み取り数を報告する運用になっている

## 6. 実行手順

以下は将来の個別承認後に実施する手順であり、この文書作成時には実行しない。

1. 作業ツリー、対象コミット、スクリプトのチェックサムを記録する。
2. 対象プロジェクトIDと認証主体を二者確認する。
3. リポジトリ外にアクセス制限された新規出力ディレクトリを用意する。
4. 短期資格情報を取得し、現在のシェルだけにプロジェクトIDを設定する。
5. 次の確認フラグ付きで1回だけ実行し、標準出力を監査JSONへ、標準エラーを別ログへ保存する。

```powershell
# 将来の承認済み作業でのみ実行する例
node scripts/audit-data.js --confirm-read-only-audit 1> AUDIT_OUTPUT.json 2> AUDIT_ERROR.log
```

6. 終了コードを記録する。非0の場合、独断で再実行しない。
7. JSONとして解析できること、`metadata.mode` が `read-only` であること、対象プロジェクトIDが一致することを確認する。
8. PIIチェックを行い、出力ファイルのSHA-256、実行日時、実行者、対象コミット、文書件数を実行記録に残す。
9. ownerId移行候補を下記基準で分類する。監査と移行は分離し、この段階ではデータを変更しない。
10. 認証情報を失効・破棄し、保存期間終了時に監査結果を削除する。

## 7. 課金見積もり

スクリプトは8コレクションに対し、それぞれフィルターなしの取得を1回行う。概算読み取り数は次の式で求める。

```text
概算文書読み取り数 = Σ max(各コレクションの返却文書数, 1)
```

空のクエリでも最低1文書読み取りとして課金される。現在のクエリは範囲フィールドを持たないため、通常はインデックスエントリ読み取りの追加課金対象外だが、実行時点の料金仕様を必ず再確認する。スクリプトには書き込みと削除がないため、それらの処理料金は発生しない。実行場所によってはネットワーク転送料が発生し得る。

| 想定データ量 | 概算 |
|---|---:|
| 全8コレクションが空 | 8 reads |
| 各コレクション100文書 | 約800 reads |
| 全コレクション合計10,000文書 | 約10,000 reads |
| 全コレクション合計50,000文書 | 約50,000 reads |

Firestoreの無料枠には、対象条件を満たす1データベースについて1日50,000文書読み取りがある。ただし、同日のサイト利用、他の監査、対象データベース、リージョン、通貨、ネットワーク料金により実料金は変わるため、無料とは断定しない。実行直前に公式料金ページとCloud Billingの予算・アラートを確認する。

## 8. 監査結果の保存方法

- 出力先はリポジトリ、GitHub Pages配下、同期共有フォルダ、公開バケットを避ける。
- 暗号化されたローカル領域またはアクセス制限済みの承認済み保管先を使う。
- ファイル名にプロジェクトID、メールアドレス、氏名を含めない。
- 実データをIssue、Pull Request、チャットへ貼らない。共有時は件数と分類結果だけを転記する。
- 生JSONの閲覧者は実行者と指名レビュー担当者に限定する。
- SHA-256を別の実行記録に保存し、改変検知に使う。
- 標準エラーログにも資格情報や文書本文がないことを確認する。
- 保存期間は原則7日、移行承認に必要な場合でも最長30日を目安とし、期限と削除責任者を記録する。
- 削除後は、ローカル、ごみ箱、バックアップ、クラウド同期先に残っていないことを確認する。

## 9. PIIを出力しない確認項目

現行スクリプトは文書全体を出力せず、件数、文書ID、所有者ID、`sourceApplicationId`、店舗名、role/status、フィールド名を中心に出力する。ただし、IDと店舗名も内部情報として扱う。

実行前後に次を確認する。

- [ ] 氏名、フリガナ、メールアドレス、電話番号、住所、生年月日を出力しない
- [ ] 応募本文、自己PR、職歴、希望条件、メッセージを出力しない
- [ ] 画像URL、プロフィール画像、身分証明書、口座情報を出力しない
- [ ] Firebase Authのユーザー一覧、メール、電話番号、トークンを取得しない
- [ ] サービスアカウントJSON、秘密鍵、アクセストークン、更新トークンを出力しない
- [ ] `applications` と `jobApplications` の文書本文を出力しない
- [ ] エラー処理が取得文書全体をシリアライズしない
- [ ] 監査JSONのキーを機械的に一覧化し、想定外のPIIフィールドがない
- [ ] 目視確認時も、生JSONを承認外の画面共有やログ収集ツールに表示しない

## 10. 実行後の認証情報破棄・無効化

### 10.1 サービスアカウント偽装を使用した場合

1. ローカルADCを失効する。

```powershell
# 将来の承認済み作業でのみ実行する例
gcloud auth application-default revoke
```

2. 実行者に一時付与した `roles/iam.serviceAccountTokenCreator` を監査用サービスアカウントから削除する。
3. 監査用サービスアカウントを再利用しない場合は、まず無効化して影響がないことを確認し、組織の保管期間後に削除する。
4. ADCで再度APIへアクセスできないことと、不要な環境変数が現在のシェルに残っていないことを確認する。

### 10.2 JSON鍵を例外使用した場合

1. Google Cloud IAMで対象の鍵IDを削除し、サーバー側で無効化する。
2. `GOOGLE_APPLICATION_CREDENTIALS` を現在のシェルから削除する。
3. ローカル鍵ファイルと一時コピーを削除し、ごみ箱、同期先、バックアップも確認する。
4. IAM上の鍵一覧から対象鍵が消えたことを二者確認する。
5. Git履歴、Actionsログ、シェル履歴、チャットへ流出していないか確認する。疑いがあれば即時失効済みであることを確認し、インシデントとして扱う。

サービスアカウントを削除するだけで鍵ファイルのコピーが消えるわけではないため、鍵のサーバー側削除とローカル破棄を両方行う。

## 11. ownerId移行判定基準

判定単位は求人1件とし、監査結果だけで実データを更新しない。候補UIDは、`users/{uid}`、`stores/{uid}`、`stores.ownerId`、`sourceApplicationId` の整合で判断する。店舗名は補助確認に限定し、単独では権限根拠にしない。

### 11.1 自動移行可能

次のすべてを満たす場合のみ、自動移行候補とする。

- 候補UIDが一意である。
- `users/{uid}` が存在し、`role == "store"` かつ `status == "active"` である。
- 対応する店舗文書が1件だけ存在し、その文書の `ownerId` が候補UIDと一致する。
- 求人の既存 `ownerId`、`storeId`、`userId` に候補UIDとの矛盾がない。
- `sourceApplicationId` を使う場合、求人と店舗の双方で一致し、店舗候補が1件だけである。
- 正規化した店舗名が一致するか、店舗名が未設定で他の強い識別子がすべて一致する。
- 同じ識別子が別店舗UIDを示していない。

### 11.2 手動確認

候補はあるが、次のいずれかがある場合は自動更新しない。

- `sourceApplicationId` は一意だが店舗名が一致しない。
- `ownerId` が `users` または `stores` の片方にしか解決しない。
- 候補ユーザーのrole/statusが欠落、`pending`、`blocked`、または `store/active` 以外である。
- `storeId` または `userId` だけがあり、他の識別子で裏付けられない。
- `ownerId`、`storeId`、`userId`、`sourceApplicationId` が異なるUIDを示す。
- 店舗名が重複している、表記揺れが大きい、または同名店舗に異なるUIDがある。
- 同じ `sourceApplicationId` を持つ複数求人があり、業務上正当か判断できない。
- 所有者不明求人に応募が紐づき、誤移行時の影響が大きい。

手動確認では、承認済みの一次資料、店舗管理者の本人確認済み申告、過去の招待・申請記録などを使用し、判断者と根拠を記録する。

### 11.3 移行不可

次の場合は所有者不明として保留し、`ownerId` を推測して設定しない。

- UIDと `sourceApplicationId` の両方で所有者を判定できない。
- `sourceApplicationId` が存在しない、対応店舗がない、または複数店舗へ対応する。
- 店舗名しか手掛かりがなく、一意で信頼できるUIDへ結び付かない。
- 複数識別子が矛盾し、信頼できる一次資料がない。
- 参照先のユーザーと店舗が両方存在しない。
- 所有者を確認できる正当な担当者または記録がない。

「移行不可」は削除を意味しない。求人を保持したまま公開・管理方針を別途決定し、データ変更には個別承認を必要とする。

## 12. 監査実行までに必要な前提条件

- [ ] リポジトリ所有者が1回の監査実行を明示承認した
- [ ] 対象プロジェクトID、日時、実行者、レビュー担当者を記録した
- [ ] `scripts/audit-data.js` のレビュー済みコミットとSHA-256を確定した
- [ ] スクリプトにFirestore/Auth/Storageの書き込み・削除処理がないと再確認した
- [ ] 8コレクション以外を読み取らないと確認した
- [ ] 読み取り専用の専用サービスアカウントを用意した
- [ ] 監査用サービスアカウントの権限が `roles/datastore.viewer` のみに限定されている
- [ ] 短期のサービスアカウント偽装を使う
- [ ] 偽装権限の付与先、付与期間、削除担当者を記録した
- [ ] 長期JSON鍵を発行しない。例外時は鍵ID、保管先、失効・削除計画を承認した
- [ ] Application Default Credentialsが意図した監査主体を指すと確認した
- [ ] `FIREBASE_PROJECT_ID` を明示し、二者照合した
- [ ] 隔離された実行環境にNode.jsと固定版 `firebase-admin` を準備した
- [ ] 読み取り件数、料金、ネットワーク転送量を見積もった
- [ ] Billing予算・アラートと当日の他処理を確認した
- [ ] リポジトリ外の暗号化・アクセス制限済み出力先を用意した
- [ ] PII禁止項目と出力スキーマをレビューした
- [ ] 保存期間、削除日、削除責任者を決めた
- [ ] 失敗時に無断再実行しない手順を共有した
- [ ] 実行後のADC失効、IAM解除、鍵削除の担当者と手順を確定した
- [ ] ownerIdの「自動移行可能・手動確認・移行不可」基準をレビュー担当者が承認した
- [ ] 監査実行とownerId更新を別作業・別承認に分離した
